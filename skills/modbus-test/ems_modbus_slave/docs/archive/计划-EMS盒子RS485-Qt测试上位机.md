# EMS盒子 RS485 Qt测试上位机计划

## 1. 目标

设计并实现一套基于 `Python + Qt` 的桌面测试上位机，通过 `USB转RS485` 连接 EMS 盒子，对 GD32 提供可视化的调试、寄存器读写、18 一体机核心功能模拟和测试流程执行能力。

该工具的定位不是完整复刻真实 18 一体机，而是优先满足以下需求：

- 快速打通 PC 到 EMS 盒子的通信链路
- 替代 18 一体机完成核心控制命令下发
- 可视化查看请求、响应、状态和日志
- 承载手工联调和后续自动化测试

## 2. 背景判断

从当前工程信息看，方案具备较高可行性：

- GD32 控制屏侧是 `Modbus RTU Slave`
- 默认从站地址为 `0x01`
- 默认波特率为 `115200`
- 控制屏通信口默认映射到 `screen_comm_port = 8`

因此，PC 侧只要通过 `USB转RS485` 正确接入 EMS 盒子的控制屏口，就可以直接使用上位机模拟 18 一体机主站，对 GD32 进行读写和联调。

## 3. 技术路线

## 3.1 推荐技术栈

- `Python 3.x`
- `PySide6`
- `pyserial`
- `pymodbus`
- `logging`
- `json`
- `csv` 或 `pandas`

## 3.2 选择 Python + Qt 的原因

- 开发速度快，适合先做测试工具 MVP
- 串口和 Modbus 库成熟
- 后续容易扩展为自动化测试平台
- 可以兼顾“人工操作”和“脚本执行”
- UI 维护成本低于纯 C++ Qt 首版

## 3.3 不建议首版采用的方案

- 直接使用 C++ Qt 全量开发
- 先做完整网页前端再转桌面工具
- 首版就做完整 18 一体机全页面复刻

原因是这些路径前期投入较大，会拖慢“先把通信和测试跑起来”的目标。

## 4. 工具定位

该上位机建议同时承担 4 个角色：

1. 串口通信调试工具
2. Modbus RTU 寄存器测试工具
3. 18 一体机核心控制模拟器
4. 测试用例执行器

换句话说，它不是一个单纯的“串口助手”，也不是一个单纯的“自动化脚本壳子”，而是一套面向联调和回归的专用测试工具。

## 5. 核心使用场景

### 5.1 场景一：基础通信联通

测试人员连接串口后，读取一个已知寄存器，确认通信、波特率、站号和接线无误。

### 5.2 场景二：手工功能联调

测试人员通过界面按钮或输入框，模拟 18 一体机下发开关机、模式切换、温度设置等命令，并观察 GD32 的响应和状态变化。

### 5.3 场景三：异常问题定位

测试人员通过界面重复发送、边界值写入、非法参数测试等方式快速复现问题，并查看详细日志。

### 5.4 场景四：自动化回归

测试人员加载测试用例文件，执行一组固定测试步骤，输出测试结果和日志。

## 8. 软件架构建议

建议采用分层设计，避免 UI 与通信逻辑耦合。

```text
UI层
  ->
应用控制层
  ->
Modbus业务层
  ->
串口通信层
  ->
USB转RS485
  ->
EMS盒子 / GD32
```

## 8.1 模块划分建议

### 8.1.1 `ui`

负责界面展示和用户交互。

### 8.1.2 `service`

负责页面动作和业务动作之间的协调。

### 8.1.3 `modbus_client`

负责 Modbus RTU 的封装，包括读、写、异常处理和超时处理。

### 8.1.4 `device_profile`

负责寄存器定义、常用命令映射和 18 一体机模拟控制项配置。

### 8.1.5 `test_runner`

负责测试用例执行、结果统计和报告生成。

### 8.1.6 `logger`

负责操作日志、通信日志和测试日志输出。

## 10. 通信可行性分析

## 10.1 可行条件

该方案成立的前提是以下条件满足：

- USB 转 RS485 模块驱动正常
- 接线正确
- EMS 盒子控制屏口已确认
- 波特率和从站地址与固件配置一致
- 至少掌握一批可验证的关键寄存器

## 10.2 可能风险

- A/B 线接反导致完全不通
- 转换器自动收发方向兼容性不好
- 实际串口参数与默认配置不一致
- 当前固件已修改控制屏端口映射
- 某些寄存器写入后受业务逻辑保护，不会立即生效

## 10.3 风险缓解建议

- 首次联调只验证读 1 到 3 个安全寄存器
- 准备一份最小寄存器验证清单
- 每次测试绑定固件版本
- UI 中显示完整错误信息和超时信息

## 11.2 第二步：18 一体机核心模拟

目标：

## 11.3 第三步：测试执行器

目标：

- 可以加载并执行测试流程

输出：

## 12. 推荐开发顺序

1. 先做串口连接和 Modbus 读写
2. 再做一体机模拟按钮区
3. 再做关键状态读取区
4. 再做测试执行器
5. 最后做日志导出和配置持久化

这样的顺序有两个好处：

- 一开始就能尽快验证硬件链路
- 每一步都有独立可交付成果

## 14. 结论

使用 `Python + Qt` 开发 EMS 盒子测试上位机是可行且推荐的方案。

该方案兼顾以下目标：

- 快速验证 USB 转 RS485 直连可行性
- 支撑 GD32 联调
- 模拟 18 一体机核心控制行为
- 为后续自动化测试留出扩展空间

因此，建议先以 `MVP` 方式启动，优先完成“连接、读写、日志、核心控制模拟”四项能力，再根据联调反馈逐步扩展。
