# 18一体机模拟逻辑实现计划

## 1. 目标

在现有 `EMS Modbus Slave` 第一版桌面从站模拟器基础上，逐步实现“18 一体机”的业务模拟逻辑，使其不仅能返回静态寄存器值，还能根据主站写入命令产生合理的状态变化、寄存器联动和场景切换行为。

本阶段目标不是完整复刻真实 18 一体机全部功能，而是优先构建一个可联调、可观察、可扩展的最小可用模拟逻辑。

## 2. 当前现状

当前已经具备以下基础能力：

- Modbus RTU 从站基础通信
- 支持 `FC03 / FC06 / FC10`
- UI 可查看和编辑寄存器值
- 内置一个 `18 Integrated Unit` profile
- 控制寄存器与状态寄存器已有最基础绑定

当前缺失的部分主要是：

- 18 一体机内部状态对象
- 写寄存器后的业务联动
- 场景化状态变化
- 故障逻辑
- 更真实的状态返回规则

## 3. 本阶段要解决的问题

第一版静态寄存器模拟只能满足“协议通不通”的验证，无法很好支撑以下场景：

- GD32 写入开机命令后，18 一体机状态应发生变化
- GD32 修改模式或目标温度后，应读回匹配状态
- 出现故障时，状态寄存器应反映故障态
- 在不同场景下，温度、运行状态、风速等应有不同表现

因此需要引入“模拟逻辑层”。

## 4. 实现原则

实现时遵循以下原则：

1. 先做最小闭环，不一开始追求完整。
2. 先建立内部状态，再映射到寄存器，不直接用寄存器数组硬拼业务逻辑。
3. 保持寄存器定义与模拟逻辑解耦，方便后续替换真实寄存器表。
4. UI 只负责展示和操作，不承载业务规则。
5. 首期逻辑必须便于后续新增场景和异常注入。

## 5. 实现范围

## 5.1 首期必须实现

- 开关机逻辑
- 模式切换逻辑
- 目标温度设置逻辑
- 风速设置逻辑
- 运行状态更新
- 故障码写入与状态反映
- UI 状态同步显示

## 5.2 首期建议实现

- 场景预设
- 状态联动规则
- 寄存器写入范围校验
- 只读寄存器保护
- 故障态下部分状态锁定

## 5.3 首期暂不实现

- 复杂时序控制
- 温度缓慢爬升/下降曲线
- 大量真实保护条件
- 复杂机组联动算法
- 云端或网页联动逻辑

## 6. 总体设计

建议将模拟逻辑拆成三层：

```text
Modbus寄存器层
  ->
18一体机状态层
  ->
18一体机业务规则层
```

### 6.1 寄存器层

负责：

- 保存当前寄存器值
- 处理主站读写
- 做基础地址和权限校验

### 6.2 状态层

负责：

- 存放 18 一体机的业务状态
- 让 UI 能直接读取明确语义的字段

建议状态字段至少包括：

- `power_on`
- `mode`
- `target_temp_x10`
- `fan_level`
- `running_state`
- `fault_code`
- `indoor_temp_x10`
- `coil_temp_x10`

### 6.3 业务规则层

负责：

- 当某个寄存器被写入时如何更新状态
- 当状态变化时如何回写相关寄存器
- 不同模式下返回什么运行状态
- 故障态时哪些字段被强制修改

## 7. 第一阶段实现内容

## 7.1 阶段目标

建立“最小状态机”，实现基础控制到状态回显的闭环。

## 7.2 具体内容

- 新增 18 一体机状态对象
- 新增寄存器到状态的映射
- 新增状态到寄存器的同步函数
- 写入控制寄存器时更新状态
- 状态变化时更新显示寄存器

## 7.3 首期最小闭环

建议先只跑通以下闭环：

1. 写开关机寄存器
2. 更新 `power_on`
3. 同步到 `power_state`
4. UI 刷新

然后逐项增加：

- 模式
- 目标温度
- 风速
- 故障码

## 8. 第二阶段实现内容

## 8.1 阶段目标

让模拟器开始具备“像设备一样”的行为，而不是简单值透传。

## 8.2 具体内容

- 开机后运行状态切换
- 关机后恢复待机状态
- 不同模式下返回不同 `running_state`
- 写故障码后强制进入故障态
- 故障态时部分命令不生效或状态受限

## 9. 第三阶段实现内容

## 9.1 阶段目标

引入可复用的场景能力，方便联调和问题复现。

## 9.2 场景建议

- `待机`
- `开机运行`
- `制热`
- `制冷`
- `故障`

## 9.3 每个场景建议定义

- 电源状态
- 模式
- 目标温度
- 当前温度
- 盘管温度
- 风速
- 故障码
- 运行状态

## 10. 第四阶段实现内容

## 10.1 阶段目标

支持更贴近联调场景的问题定位和回归验证。

## 10.2 具体内容

- 异常码返回
- 超时不响应
- 只读寄存器拒写
- 特定场景锁值
- 快照导入导出

## 11. 推荐开发顺序

建议按下面顺序推进：

1. 定义状态对象
2. 定义寄存器到状态映射
3. 定义状态到寄存器同步
4. 实现开关机逻辑
5. 实现模式逻辑
6. 实现目标温度逻辑
7. 实现故障逻辑
8. 实现场景预设
9. 实现异常注入

## 14. 如果资料暂时不全

如果真实寄存器表暂时拿不到，可以先按现在第一版内置的占位寄存器继续推进。

这种情况下实现策略是：

1. 先完成一版“逻辑骨架”
2. 所有控制逻辑先基于当前 profile 中的占位寄存器
3. 等真实寄存器表到位后，再替换映射关系

这样可以先把架构和交互跑通，不会因为等协议资料而完全停住。

## 15. 验收标准

本阶段完成后，至少应满足以下标准：

1. 写开关机寄存器后，状态和显示寄存器同步更新。
2. 写模式寄存器后，模式状态可正确读回。
3. 写目标温度寄存器后，目标温度状态可正确读回。
4. 写故障码后，模拟器进入故障态并能读回故障码。
5. UI 状态面板与寄存器状态保持一致。
6. 逻辑结构支持后续继续加场景和异常，而不需要大改主框架。

## 17. 结论

当前最合理的做法不是继续堆更多静态寄存器，而是正式引入“18 一体机模拟逻辑层”。

这样做的收益是：

- GD32 联调更真实
- 问题复现更稳定
- UI 更容易扩展
- 后续新增别的从站模型时可以复用同一套架构

本计划建议先以“最小状态机 + 关键寄存器联动”为第一目标，在此基础上逐步走向场景化和异常化模拟。
