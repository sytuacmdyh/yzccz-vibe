# 从站模拟器完整计划（首期仅实现 18 一体机）

## 1. 文档目标

规划一套可扩展的“从站模拟器”方案，用于在 PC 侧模拟 EMS 盒子外部设备，帮助 GD32 联调、回归测试和异常复现。

本计划强调两点：

1. 平台目标是“通用从站模拟器”，不是只做一个临时脚本。
2. 首期实现范围严格收敛为“18 一体机”一种设备模型，先把最有价值的链路跑通。

## 2. 背景与问题定义

当前联调存在几个典型问题：

- 真实外设不一定随时可用
- 现场联调依赖硬件齐套，成本高
- 问题复现难，尤其是边界值和异常报文
- 手工测试不容易沉淀为标准回归流程

因此需要一套桌面端从站模拟器，用来在电脑上模拟真实设备的寄存器、状态机和响应行为，让 GD32 可以像面对真实设备一样完成轮询、读写和逻辑处理。

## 3. 平台定位

该工具的定位是：

- 一个可视化的从站模拟平台
- 一个可配置的协议响应器
- 一个可注入异常的联调工具
- 一个可复用的测试夹具

首期不是做“全设备大而全平台”，而是做“框架先对，先落 18 一体机”。

## 4. 首期范围

## 4.1 首期只实现的设备

- `18 一体机`

## 4.2 首期实现目标

- 能在 PC 上启动一个 18 一体机从站模拟实例
- 能通过 `USB 转 RS485` 与 GD32 建立通信
- 能按预设寄存器表响应 GD32 请求
- 能通过 UI 修改关键状态和关键寄存器
- 能记录完整收发日志
- 能模拟基础异常场景

## 4.3 首期明确不做

- 同时实现电表、水表、流量计、热源等全部从站
- 完整复刻真实 18 一体机所有内部算法
- 首版就实现多协议并存
- 首版就实现复杂脚本系统

## 5. 为什么首期只做 18 一体机

这是一个故意收敛范围的决定，原因如下：

- 18 一体机是当前最直接的联调对象
- 价值最高，最能帮助验证 GD32 主流程
- 先做一个真实可用的设备模型，能反向验证平台架构
- 如果第一版就把所有从站都纳入，会导致需求发散、周期失控

也就是说，首期的真正目标不是“少做功能”，而是“用 18 一体机把从站模拟平台的骨架做对”。

## 6. 总体设计目标

平台后续要支持从“单设备模拟器”演进到“多设备模拟平台”，因此架构上需要提前满足以下目标：

- 设备模型可插拔
- 寄存器表可配置
- 协议行为可扩展
- UI 可根据设备模型动态生成
- 支持手工控制和测试流程驱动
- 支持正常响应与异常响应

## 7. 目标使用场景

## 7.1 场景一：GD32 联调

GD32 作为主站，轮询 18 一体机从站。PC 模拟器返回寄存器值，供 GD32 完成功能联调。

## 7.2 场景二：问题复现

通过人工修改模拟器中的寄存器值或状态，让 GD32 进入特定路径，复现现场问题。

## 7.3 场景三：异常联调

模拟超时、异常码、非法数据、状态跳变，用于验证 GD32 的容错逻辑。

## 7.4 场景四：回归测试

配合测试脚本或测试上位机，固定输入输出，验证每次改动没有引入回归问题。

## 8. 技术路线

## 8.1 推荐技术栈

- `Python 3.x`
- `PySide6`
- `pyserial`
- `pymodbus`
- `json`
- `logging`

## 8.2 原因

- Python 适合快速做协议模拟器
- Qt 适合做设备状态可视化和调试界面
- pymodbus 能降低从站实现复杂度
- 便于后续和现有 Python 测试脚本共用能力

## 8.3 通信形态

首期默认采用：

- PC
- USB 转 RS485
- EMS / GD32

后续可扩展：

- TCP 到串口桥接
- 多串口实例
- 多设备并行模拟

## 10. 架构设计

建议将系统拆成五层。

```text
UI 层
  ->
模拟器控制层
  ->
设备模型层
  ->
协议适配层
  ->
串口传输层
```

## 10.1 UI 层

负责：

- 配置界面
- 状态显示
- 寄存器编辑
- 日志展示

## 10.2 模拟器控制层

负责：

- 启停模拟器
- 应用配置
- 驱动设备模型
- 分发 UI 操作

## 10.3 设备模型层

这是本方案的核心。

每种设备模型都要描述：

- 设备名称
- 默认地址
- 支持功能码
- 寄存器表
- 状态机
- 写入联动规则
- 异常行为配置

首期只提供一个设备模型：

- `Profile18IntegratedUnit`

## 10.4 协议适配层

负责：

- Modbus RTU 报文处理
- 功能码解析
- CRC
- 异常响应组包

## 10.5 串口传输层

负责：

- 打开串口
- 关闭串口
- 收发数据
- 超时与异常上报

## 11. 18 一体机模型设计

首期建议把 18 一体机模型分成三部分：

## 11.1 寄存器定义

包括但不限于：

- 控制类寄存器
- 设定值寄存器
- 状态类寄存器
- 故障类寄存器

## 11.2 状态对象

建议内部用一个明确状态对象管理，而不是把一切都直接堆在寄存器数组里。

例如：

- `power_on`
- `mode`
- `target_temp`
- `fault_code`
- `running_state`

这样做的好处是：

- UI 更容易绑定
- 行为规则更容易维护
- 后续场景切换更简单

## 11.3 联动规则

需要定义“写入某寄存器后，哪些状态会变化”。

例如：

- 写开关机寄存器后更新 `power_on`
- 写模式寄存器后更新 `mode`
- 写目标温度寄存器后更新 `target_temp`
- 当故障注入开启时，状态寄存器返回故障值

## 13. 数据文件规划

建议把设备定义和测试配置从代码中抽出来，避免以后新增设备时大量改代码。

## 13.1 设备模型文件

## 13.2 场景文件

## 13.3 异常模板文件

用于定义：

- 某地址超时

- 某次请求返回坏包

## 16. 风险与约束

## 16.1 需求风险

- 18 一体机寄存器定义可能还在变化
- 某些行为规则文档化不足

## 16.2 技术风险

- USB 转 RS485 兼容性问题
- 部分从站库对异常包模拟支持有限

## 16.3 范围风险

- 很容易从“先做 18 一体机”膨胀成“顺手把别的设备也做了”

因此需要明确里程碑：

- 第一里程碑只验收 18 一体机
- 不因未来扩展需求干扰首期交付

## 17. 验收标准

首期完成后，至少应满足以下验收条件：

1. 模拟器可通过串口稳定启动和停止。
2. GD32 可对模拟器执行基础读写。
3. 18 一体机关键寄存器可正确响应。
4. UI 可修改关键状态并立即生效。
5. 通信日志可查看和导出。
6. 至少支持 2 到 3 类异常注入。

## 19. 结论

这份计划的核心结论是：

- 我们要做的是“通用从站模拟器框架”
- 但首期必须只实现“18 一体机”
- 18 一体机不是临时特例，而是首个设备 Profile
- 平台架构从第一天开始就要为后续扩展留好接口

这样做，既能尽快支撑当前 GD32 联调，也不会把后续多从站扩展路线堵死。
